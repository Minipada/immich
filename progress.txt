Issue #7: Quality signals and read-time hallucination filtering

Every segment now carries three signals from the model, every segment is
stored whatever they say, and the caption track excludes the failures when
it is read. All eight acceptance criteria are covered.

ML side (immich_ml/models/transcription/whisper.py, schemas.py):
- `no_speech_prob`, `avg_logprob` and `compression_ratio` are already on
  every faster-whisper segment; they are passed through as decoded, under
  the same names the rest of the transcript uses.
- Passed through, not acted on. faster-whisper applies thresholds of its
  own while decoding, but only to pick a temperature to retry at — it
  emits the segment either way. The adapter stays a reporter for the same
  reason it does with language confidence: the decision is the server's.

The filter (server/src/utils/transcription.ts, `filterHallucinations`):
- Discard when no-speech probability is above its threshold AND average
  log-probability is below its own. Either alone has an innocent reading —
  a high no-speech probability also describes quiet but genuine speech, a
  low log-probability also describes speech the model found hard (an
  accent, a crowd, a bad microphone) — so pairing them is what stops the
  rule firing on real speech. Together they say the model neither heard
  speech nor believed what it wrote down.
- Discard when compression ratio is above its threshold, on that signal
  alone. Compression ratio is text length over compressed size, so nothing
  but a repetition loop reaches a high value; there is no innocent reading
  to pair it against.
- At a threshold exactly the segment is kept. The settings read as the
  worst still tolerated, so discarding at the boundary would be off by one.
  Same reasoning as `minLanguageConfidence` in issue #6, opposite direction.
- No phrase blocklist, as the issue specifies. It would be per-language,
  unbounded, and a maintenance treadmill; the numbers identify the same
  segments for a reason that holds in every language.
- A segment whose signals are null is kept. Null means "written before this
  change", not "scored zero" — judging on a missing number would silently
  blank every transcript made before this branch. The paired rule needs
  both signals present, so a half-recorded segment is kept too.

Read time, not ingest (asset.service.ts, transcription.service.ts):
- `transcribeChunk` writes every segment the model returned, signals
  included, and never inspects them.
- `getCaptions` reads the config alongside the segments and filters there.
  Changing a threshold changes what the next request renders; nothing is
  re-transcribed. That is the one-way-door argument from the issue: rows
  can be re-derived into a caption track, but inference discarded has to be
  re-run across the whole library to get back.
- Search is not touched. The issue names it as a later slice.

Schema and config:
- `transcript_segment.noSpeechProbability`, `avgLogProbability`,
  `compressionRatio`, all nullable `real` (migration 1785447598281).
  Nullable only for segments written before this change. Written by hand
  because the build was broken here (see caveats), then verified: the
  migration applies cleanly and `migrations:generate` afterwards reports
  "No changes detected", so it matches the table definition exactly.
- `machineLearning.transcription.maxNoSpeechProbability` (0.6),
  `minAvgLogProbability` (-1), `maxCompressionRatio` (2.4). These are
  Whisper's own decoding defaults, which is the only calibration anyone has
  for these three numbers; nothing here argues for departing from them
  before there is evidence.
- OpenAPI spec, TypeScript SDK client and SQL query snapshots regenerated.
- No administrator UI: issue #13 covers transcription settings, same as the
  chunking and language settings before it.

Tests:
- 11 unit tests on the filter: each rule independently, each half of the
  paired rule retained on its own, both halves failing, the repetition rule
  alone, every threshold exactly, a mixed transcript, empty input, null
  signals, half-recorded signals, and the same rows judged differently by
  changed thresholds.
- 4 asset-service tests on `getCaptions`: passing segments rendered, a
  hallucinated one excluded, thresholds changed without re-running
  inference, and progress still reported when everything is filtered out.
- 2 transcription-service tests: signals stored per segment, and a segment
  every threshold would reject still persisted.
- 3 medium tests: signals round-trip through the database, a rejected
  segment is stored, and a segment written without signals reads back null.
- 1 new ML test that a segment scoring badly on all three is reported
  rather than withheld; the existing transcription tests moved onto a
  `whisper_segment` helper so a decoded segment carries the new fields.
- Full server unit suite green (2319 passed, 2 skipped). ML suite green
  (115 passed, 3 skipped). Server lint/format/typecheck, web svelte-check,
  and ML ruff/mypy --strict all green.

Also fixed: `system-config.service.spec.ts` asserts the whole default
config object, so the three new defaults had to be added there.

Not done / caveats:
- Thresholds are global, not per-asset or per-language. The signals are
  per-segment in the database, so narrowing that later is a config change
  rather than a schema change.
- The filter is applied to the caption track only. Search indexing of
  transcripts does not exist yet; when it does it should use the same
  function, which is why it takes any object carrying the three signals
  rather than a segment row.
- Defaults are inherited from Whisper rather than tuned against a corpus of
  real hallucinations. Retuning is now cheap by construction, which is the
  point of the slice, but somebody should still look at real output.
- The workspace was in a broken state on arrival, unrelated to this issue:
  `@immich/sdk` and `@immich/plugin-sdk` had no build output, which fails
  every server test and every server build. Both were rebuilt (sdk first,
  plugin-sdk depends on it). Worth knowing before blaming a branch.
- The medium-test harness still cannot start its own database here:
  testcontainers fails against this host's Docker with "Log stream ended",
  as it did on the previous issue and on a clean checkout. The medium tests
  were run against the running `ghcr.io/immich-app/postgres` with a
  throwaway global setup pointed at it; all 16 in the transcript suite pass.
  The throwaway setup was deleted and is not part of the commit.
- The Dart SDK was not regenerated: `openapi-generator-cli` is unavailable
  here, and `mobile/openapi` already lacked `TranscriptionConfig`, so this
  branch does not make it any staler.
