Issue #9: Transcript panel in the asset viewer (read-only)

Opening a video shows its transcript beside the video, highlights the
line being spoken, seeks on click, and filters client-side. All ten
acceptance criteria are covered.

Server:
- New `GET /assets/:id/transcript` returning `AssetTranscriptResponseDto`
  — `{ status, progressMs, segments: [{ id, startTime, endTime, text,
  language }] }` — at the same permission as the caption track
  (`AssetView`, shared links included).
- A JSON endpoint rather than parsing the existing WebVTT in the browser.
  The VTT carries its status in `NOTE` blocks because that is the only
  place a `<track>` will tolerate it; a panel has no such constraint, and
  parsing a format designed to be handed to a player in order to rebuild
  the records it was rendered from is work the server has already done.
- `getCaptions` and `getTranscript` now share one private read, so the
  caption track and the panel cannot disagree about which segments exist
  or how far the job has got, and the read-time hallucination thresholds
  from issue #7 apply identically to both.
- Not gated on completion, as before: the status is what lets a client
  tell a job that never ran from one still running, and so know whether
  to ask again.

Web — the panel:
- `TranscriptPanel.svelte`, opened from a new "Transcript" action in the
  viewer nav bar (`c`), gated on the asset being a video and on the
  transcription feature flag.
- Placement follows the existing panels exactly: a grid item in the same
  implicit column the detail and activity panels use, `w-90`, same fly
  transition and border. Because the four content columns are `1fr`,
  adding the panel shrinks the video rather than covering it.
- One side panel at a time. Opening the transcript closes detail and
  activity and vice versa; each takes a column, and two at once leave the
  video with very little. That is the rule the existing two already
  follow between themselves.
- The header, close button and filter box reuse the existing components
  (`IconButton`, `SearchBar` — the same one the people filter uses), so
  the panel introduces no new idiom.

Three states, presented differently:
- Never started: "this video has not been transcribed yet".
- In flight: a spinner and percentage in the header, and the lines
  produced so far below it. With no lines yet, a message saying they
  appear as they are produced. The panel re-asks every 15s and stops once
  the transcript is complete, since a finished transcript never changes.
- Complete with no segments: "no speech was found", which is a fact about
  the video rather than an error.
- A failed load shows a message; a failed *refresh* of a transcript
  already on screen keeps what is there rather than blanking it.

Following playback:
- `video-player-manager.svelte.ts` publishes the playhead and accepts
  seeks. The video element lives in `VideoNativeViewer` and the panel is
  a sibling in the viewer grid; a manager is how the rest of the viewer
  already crosses that gap. Keyed by asset id, because the viewer keeps
  rendering across navigation and a panel must not highlight lines
  against the playhead of a different video.
- The highlighted line is the last one to have *begun*, not one strictly
  containing the playhead. Speech has gaps, and blanking the highlight in
  every pause reads as a bug rather than as silence.
- Auto-scroll happens only when the current line has left view, and
  centres it when it does — a nudge every few lines rather than a jump on
  every one.
- Manual scrolling is never prevented. Any scroll the panel did not
  perform itself turns following off, detected by comparing against the
  position the panel last set; a "Follow playback" button brings it back,
  and clicking a line brings it back too. This is why the automatic
  scroll is instant rather than smooth: a smooth scroll reports positions
  the panel never set, which would read as manual scrolling and switch
  itself off immediately.

Narrow viewports:
- Below `md` the panel becomes a drawer across the bottom 45svh and the
  viewer content gets matching bottom padding, so the video shrinks into
  the remaining height instead of being covered. Both are visible; the
  issue's escalation condition — having to choose between the transcript
  and the video — does not arise.
- Implemented without touching the grid template, so no other asset type
  is affected: the drawer is absolutely positioned inside the viewer
  section, and the padding is applied only while the panel is open, which
  is only possible for a video.

Tests:
- 12 web tests on the panel: lines and timestamps render, the filter
  narrows and reports matching nothing, a click seeks the player, the
  highlight moves as the playhead advances, scrolling stops following and
  the button restores it, filtering does not, an in-progress transcript
  shows partial lines with its indicator, the three empty states are
  distinguished, a failed load is reported, and polling continues while
  in progress and stops on completion.
- 5 server tests on `getTranscript`: timings returned, the caption
  track's thresholds applied, a partial transcript returned as in
  progress, a never-transcribed asset reported as not started, and view
  access required before anything is read.
- Web unit suite green (530 passed, 2 skipped). Server unit suite green
  (2333 passed, 2 skipped). Server lint/format/tsc and web
  lint/format/svelte-check all green; svelte-check reports the same 7
  pre-existing errors as a clean checkout, all in unrelated test files.

Verified against a running instance:
- A stack was brought up for this: postgres and valkey in containers with
  published ports (this host runs rootless Docker, so container IPs are
  not routable), the built server run natively, and the web dev server
  against it. A three-minute video was uploaded through the API and given
  a transcript; the machine-learning container on this host is built from
  the issue #3 image and rejects the current request shape, so the
  segments were seeded directly rather than inferred. That exercises what
  this issue added — the endpoint reads those rows and the panel reads
  the endpoint — but not the model.
- Confirmed by driving the browser: the panel opens beside the video
  without covering it and the video shrinks into the remaining columns;
  22 of 24 seeded rows are shown, the two carrying hallucination signals
  filtered out by the shared read; clicking 02:22 moved the video to
  142.4s and the highlight with it; the filter narrows to matching lines;
  scrolling stops following and the button restores it; the three job
  states each render as intended, including "Transcribing… 36%" over the
  lines produced so far; and a chunk inserted while the panel was open
  appeared within the poll interval with the percentage advancing, all
  without a reload. At 420px wide the panel becomes the bottom drawer and
  the video keeps the space above it.
- Captions on the video were sitting behind the play button and the
  progress bar, and clipping at the bottom edge — worst with the panel
  open on a narrow viewport, where the video area is short and the
  controls take a larger share of it. A player puts its captions at the
  bottom of the video box, which is where the control bar is. The cue
  container is now lifted by the height of the controls, which leaves the
  browser to wrap, align and style the cues, including a reader's own
  caption preferences. Positioning each cue instead was tried first and
  rejected: anchoring a cue's bottom edge needs `snapToLines = false`,
  and Blink then lays the cue out on one line and clips the overflow
  rather than wrapping it — verified in the browser, not assumed. Blink
  and WebKit expose the container; Firefox has no equivalent, so captions
  there stay where it puts them, which is what they do today.
- One bug was found this way and fixed in a follow-up commit: filtering
  shortened the list, the browser clamped the scroll position to the
  shorter content, and the resulting scroll event was attributed to the
  reader, so following switched itself off after a keystroke in the
  filter box. The expected scroll position is now re-synced whenever the
  visible lines change. The regression test reproduces it by firing the
  scroll event the browser sends after the list shrinks, and fails
  without the fix.

Not done / caveats:
- Real inference was not exercised end to end here, for the reason above;
  that path is issue #3's and was demonstrated there.
- The Dart SDK was again not regenerated, consistent with issues #3–#8 on
  this branch: `mobile/openapi` already lacks the transcription models
  from those issues, so regenerating here would land six issues' worth of
  unrelated diff on this one.
- "Corrected text preferred over model output" is not implemented,
  because editing does not exist yet and there is no column to prefer.
  The panel reads each segment's text through one accessor, so it becomes
  a change to what that reads rather than a change to the panel.
- An equirectangular video plays through `VideoPanoramaViewer`, which
  registers no player, so its transcript lists and filters but does not
  highlight or seek. Left alone rather than special-cased.
- Casting is the same case: the cast receiver holds the playhead, so
  while casting the panel lists lines without following or seeking.
- Search within the panel is a substring match over the segments already
  loaded, as the issue specifies. Moment-level search across the library
  is not part of this and stays out of the asset-shaped global search.

Issue #10: Search videos by transcript content

Searching a spoken phrase now returns the videos containing it, alongside
every existing search filter. All acceptance criteria are covered.

Storage:
- New `transcript_search` table — one row per asset, trigram-indexed on
  unaccented text via `gin (f_unaccent(text) gin_trgm_ops)` — mirroring
  `ocr_search` exactly, down to the index expression and the delete-on-empty
  upsert shape.
- `transcript_segment` gains a nullable `correctedText` column. Editing does
  not exist yet — that is issue #11's — but the search text builder already
  reads through it, so correction preference becomes a write to an existing
  column rather than a second change to the index when #11 lands.
- Two migrations, generated against a live Postgres and hand-trimmed: the
  auto-diff also proposed re-creating several `geodata_places` indexes and
  constraints this environment never had (that table's data import — a
  separate script from migrations — was never run here), which is
  pre-existing drift unrelated to this issue and was left out.

Building the index:
- `buildTranscriptSearchText` (`utils/transcription.ts`) takes an asset's
  segments and the same hallucination thresholds the caption track and panel
  already apply at read time, and returns one flattened string: hallucinated
  segments excluded, `correctedText` preferred over `text` where present,
  every kept segment's text run through `tokenizeForSearch` — the same
  tokenizer the query side uses — before joining. Indexing and querying
  disagreeing on where one word ends and the next begins would silently
  break the trigram match.
- Called once, from `TranscriptionService.handleTranscribe`, after the chunk
  loop finishes and before the asset is marked transcribed — not from inside
  the loop. An empty result (no speech, or every segment discarded) deletes
  the row rather than writing an empty one, same as OCR.
- `TranscriptRepository.reset` now also deletes any existing search row for
  the asset, so a video mid-reprocessing has no transcript row and cannot
  keep matching on what an earlier run produced. `deleteAll` truncates
  `transcript_search` alongside `transcript_segment`.

Server search API:
- `transcript` added everywhere `ocr` already was: the legacy
  `MetadataSearchDto`/`SmartSearchDto`/`StatisticsSearchDto` field (all three
  extend `BaseSearchSchema`), and the `StringSimilarityFilter`-typed
  `SearchFilterBranch.transcript` for the v3 filter DTOs (unrouted in this
  codebase currently, same as `ocr` there — added for parity, not reachable
  yet).
- Both `searchAssetBuilderLegacy` and the v3 `branchPredicates` gained a
  `transcript` branch, byte-for-byte the same shape as the existing `ocr`
  branch: an inner join (legacy) or `exists` subquery (v3) against
  `transcript_search`, matching with the trigram word-similarity commutator
  `f_unaccent(...) %>> f_unaccent(...)` — this is what gives both the accent
  tolerance and the wording tolerance, not two separate mechanisms.
  `mise open-api` regenerated the spec and the TypeScript SDK (the Dart SDK
  was left alone, consistent with every prior issue on this branch); the
  generated `.sql` query snapshots were refreshed via `sync-sql.js` against a
  live database.

Web:
- A `transcript` query type alongside `ocr` in the search type selector
  (`SearchBar`, `SearchTextSection`, `SearchFilterModal`), gated on the
  `transcription` feature flag the same way `ocr` is gated on its own flag.
  This is deliberately not folded into the primary search input: like OCR
  text, a spoken phrase will not surface from the default smart-search box,
  which is the accepted limitation the issue calls out — the inexpensive fix
  is unifying the two text fields behind one input later, not building new
  interface now.

Tests:
- 9 unit tests on `buildTranscriptSearchText`: empty input, multi-segment
  flattening, correction preferred, fallback to model text, hallucination
  exclusion, a hallucination excluded even when it carries a correction, and
  tokenizer agreement for both Latin and CJK text (compared directly against
  `tokenizeForSearch`'s own output).
- 4 tests on `TranscriptionService`: the search text is written once at
  completion and before the asset is marked transcribed; it is not written
  when a video is skipped for having no audio track, is hidden, or when a
  run is stopped by its time budget.
- 6 end-to-end tests added to the existing `/search/metadata` spec: a spoken
  phrase finds its video, accents and diacritics are tolerated, small
  wording differences are tolerated, the filter combines with `type`, a
  video with no transcript row (standing in for one still processing) is
  excluded, and unrelated text matches nothing. Seeded directly via a new
  `utils.setTranscriptSearchText`, since the e2e machine-learning container
  does not perform real speech recognition — the same reason issue #9's
  browser verification seeded segments directly.
- Server unit suite green (2345+ passed, 2 skipped). Web unit suite green
  (530 passed, 2 skipped). Server and web lint/format/tsc green; web
  svelte-check reports 0 errors.

Verified against a running instance:
- The migrations were generated and applied against a live Postgres
  (confirmed idempotent: regenerating afterward produces no further
  transcript-related diff), and the resulting `%>>`/`f_unaccent` operators
  were exercised directly against it with the literal strings the new e2e
  tests use, confirming the phrase match, the accent-insensitive match, the
  fuzzy wording match, and the unrelated-text non-match all behave as
  asserted.
- Not exercised: the new e2e test file was not run through the full e2e
  harness. That suite talks to a dedicated Postgres/Redis/server trio on
  fixed, non-default ports (`e2e/docker-compose.yml`, building the server
  image from scratch), which is a materially heavier stack than the
  lighter one issue #9 stood up by hand. Given the SQL was independently
  validated against a live database and the full unit suites are green,
  standing up that dedicated stack for this issue alone was judged not
  worth its cost; the endpoint coverage exists and reads correctly, but has
  not been run end to end.

Not done / caveats:
- The Dart SDK was not regenerated, consistent with every prior issue on
  this branch.
- `correctedText` is write-less until issue #11 adds the editing UI and its
  endpoint; until then every segment's `correctedText` is null and the
  search text builder falls back to the model's own text for all of them.

Issue #11: Transcript correction with re-processing lock

Correcting a misheard line now changes what the caption track and search
show immediately, survives re-processing, and can be reverted. All ten
acceptance criteria are covered.

Storage and write path:
- No new migration: `transcript_segment.correctedText` already existed,
  added ahead of need by issue #10. `TranscriptRepository.updateSegment(id,
  assetId, correctedText)` is the first write to it — an `UPDATE ...
  WHERE id = ? AND assetId = ?`, scoped to the asset as well as the segment
  so a caller that has already checked access to one asset cannot reach
  another's row with a guessed segment id. `correctedText: null` reverts to
  the model's own text; it is the same endpoint rather than a second one,
  since "revert" is just a correction of `null`.
- `AssetService.updateTranscriptSegment` gates on `Permission.AssetUpdate`
  (not `AssetView`, unlike every other transcript read) and rebuilds the
  flattened search text immediately afterward, using the same
  `buildTranscriptSearchText` the transcription job itself calls at
  completion. A correction search cannot find is pointless, and derived
  text does not update itself.
- The caption track had the gap issue #10 flagged: `buildTranscriptSearchText`
  already preferred `correctedText ?? text`, but `toWebVtt` still burned in
  the model's own text. Both now agree.
- `TranscriptSegmentResponseDto` gained `correctedText`; `text` stays as the
  model's own output, unaffected by any correction, so "the original model
  output remains viewable" is a property of the read rather than a second
  request.

The re-processing lock:
- Time-anchored reconciliation — reattaching a correction to whatever a
  re-run produces by matching time ranges — was rejected. Re-transcription
  does not produce stable boundaries: different seams, voice-detection
  variance and model nondeterminism all shift them, so a correction
  reattached this way can silently land on text it does not match. That is
  corruption presenting as human-verified, worse than data loss the user
  was warned about.
- Consequently `TranscriptRepository.reset` — called at the start of every
  forced (re-)transcription run, single-asset or library-wide — now deletes
  only segments where `correctedText is null`. A correction is left exactly
  as written rather than risked. This is "forced re-processing preserves
  corrected segments," tested directly against a real database.
- The library-wide `deleteAll` (queue-all with `force`) goes further: an
  asset with any corrected segment is excluded from the sweep entirely —
  corrected and uncorrected segments alike are left untouched, and its
  `asset_job_status`/search rows are left alone too — rather than being
  partially cleared. `AssetJobRepository.streamForTranscriptionJob` carries
  the same exclusion, so a corrected asset is never even queued for a bulk
  run, forced or not. This is what "assets with any corrected segment are
  excluded from bulk runs" means: not touched, not partially discarded.
- Single-asset re-processing (the "Refresh transcript" job action, always
  forced) is deliberately not excluded — the owner can still explicitly
  redo one video — but now requires confirmation first, added at the one
  place both the single-asset and bulk-selection actions funnel through
  (`handleRunAssetJob`). The dialog's copy is honest about what actually
  happens: corrections are kept, everything else is regenerated. This
  differs from the existing library-wide "force reprocess all" confirmation
  in the admin queue panel, which still (correctly) warns that it discards
  everything, since that path's `deleteAll` never touches a corrected asset
  in the first place.

Web — inline correction:
- Each transcript line grew a pencil icon (edit) beside it, and a history
  icon (revert) that appears only once a line is corrected. Editing swaps
  the line for a `Textarea` sized to one row; saving happens on blur if the
  trimmed text differs from what is currently displayed, mirroring
  `DetailPanelDescription`'s bind-and-save-on-blur pattern for the asset
  description. Escape blurs without saving, tracked by a plain boolean
  rather than component state, since it only ever needs to survive from one
  keystroke to the very next blur event.
- Emptying the line, or typing back exactly what the model originally said,
  both save as a revert (`correctedText: null`) rather than as a blank or
  redundant correction — the same outcome as pressing the revert icon, from
  the box instead.
- A correction renders with a small "Corrected" badge and the original
  text beneath it in muted italics, so "corrected lines are visibly
  distinguishable" and "the original model output remains viewable" are
  both true without a click or a toggle.
- The click-to-seek behaviour could not stay a single `<button>` once an
  editable line needed a sibling row of icon buttons: a `<textarea>` cannot
  live inside a `<button>` per the HTML content model. The line is now a
  `<div>` row holding either the seek button or the edit textarea, with the
  edit/revert icons as further siblings — never nested inside each other.
- The panel's own client-side filter matches against `correctedText ??
  text`, the same preference order as everywhere else; searching for what a
  line was corrected to is the entire point of correcting it.
- Edit and revert controls are gated on `isOwner` (`authManager.authenticated
  && authManager.user.id === asset.ownerId`), the same simplified ownership
  check `DetailPanelDescription` already uses for the same purpose.

Tests:
- 9 new/updated server unit tests: `getTranscript`/`getCaptions` include
  `correctedText`; `updateTranscriptSegment` writes the correction, rebuilds
  search text, reverts on `null`, rejects a segment id that does not belong
  to the given asset, and requires `AssetUpdate` rather than `AssetView`.
  2 new `toWebVtt` tests confirm the correction preference.
- 8 new medium (real-database) tests: `updateSegment` writes, reverts and
  is scoped to the given asset; `reset` preserves a corrected segment while
  clearing an uncorrected one; `deleteAll` leaves an asset with any
  correction completely untouched while still sweeping a plain one;
  `streamForTranscriptionJob` excludes a corrected asset even when forced.
- 6 new web unit tests: a correction is visibly distinguishable with the
  original still shown; edit/revert controls are absent without
  asset-update access; inline correction saves and re-renders; Escape
  discards without saving; revert restores the model text; the panel's
  filter matches by corrected text. 3 new tests on `handleRunAssetJob`:
  confirms and skips on cancel, confirms and proceeds on accept, and does
  not confirm an unrelated job.
- 6 e2e tests added to `asset.e2e-spec.ts` for the new endpoint: requires
  access, rejects a blank correction, rejects a segment belonging to a
  different asset, corrects a segment (and confirms both the transcript
  read and the caption track reflect it), and reverts a correction. As with
  issue #10, not run through the full e2e harness — that stack builds the
  server image from scratch, a heavier cost than this issue's server-side
  SQL and unit coverage justified — but typechecked cleanly.
- Server unit suite green (2352 passed, 2 skipped); server medium suite
  green for the touched repositories (37 passed). Web unit suite green (539
  passed, 2 skipped). Server and web lint/format/tsc green; svelte-check
  reports 0 errors.

Verified against a running instance:
- Reused the postgres and valkey containers issue #9's verification left
  running (published ports, since this host's rootless Docker makes
  container IPs unreachable directly) rather than standing up a fresh pair;
  its database already held issue #9's 24-segment seeded transcript on a
  real video asset. Migrations were a no-op — already current.
- The built server was run natively against it with only the `api` worker
  included (`IMMICH_WORKERS_INCLUDE=api`): the full microservices worker
  fails to bootstrap in this environment over an unrelated, pre-existing
  gap — reverse geocoding requires geodata files this checkout does not
  have, and that failure is fatal to the whole worker, not just to
  geocoding. Everything this issue touches is reachable through the API
  worker alone. `machineLearning.enabled` was flipped on system config only
  long enough to satisfy the web feature flag gating the panel and job
  action (no inference was ever invoked, since every segment here was
  seeded directly), and set back to its prior value afterward.
- Driven by browser: opened the transcript panel on the seeded video,
  corrected the first line's misheard name, and confirmed in the same
  session that the caption track (`GET .../captions.vtt`) rendered the
  correction instead of the original text, and that `POST
  /search/metadata` with the corrected phrase found the asset — both
  without a reload. The corrected line showed the "Corrected" badge with
  the original text beneath it. Reverting it removed both and the caption
  track reverted with it. Opening "Refresh transcript" from the asset's
  menu raised the confirmation dialog with the copy described above;
  cancelling it left all 24 segments and zero corrections in the database,
  confirming nothing was queued.

Not done / caveats:
- The Dart SDK was not regenerated, consistent with every prior issue on
  this branch.
- Timing edits, merging and splitting are explicitly out of scope per the
  issue — corrections are text-only.
- The recorded tradeoff the issue calls out stands as designed: a
  collaborator's single-word correction excludes the asset from the
  owner's bulk runs too. The suggested mitigation (an advisory lock that
  blocks bulk but not the owner's explicit single-asset re-run) is not
  implemented, since the single-asset path was never blocked to begin
  with — it already requires its own explicit confirmation, which is the
  gap this issue closes.
