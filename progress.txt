Issue #8: Bulk transcription queue, job panel and completion semantics

An administrator can transcribe an existing library from the job panel,
watch it progress, and re-run a single video without touching the rest.
All nine acceptance criteria are covered.

Already in place before this issue (from the tracer bullet, #3):
- `AssetTranscribeQueueAll` streaming asset ids and enqueueing per-asset
  `AssetTranscribe` jobs in pages of JOBS_ASSET_PAGINATION_SIZE.
- `QueueName.Transcription` registered at concurrency one, wired into
  `QueueService.start` for both targeting modes, and present in the
  administrator concurrency settings.
- `streamForTranscriptionJob` already excluded hidden assets, non-videos
  and deleted assets, and already switched on `force` between "only
  unprocessed" and "all". It now has tests that say so.

Completion semantics (transcription.service.ts):
- A video with no audio track is marked transcribed rather than merely
  skipped, so bulk runs stop re-examining it. Left unmarked it is
  re-enqueued and re-dequeued by every run for the rest of the library's
  life, and a queue that runs one job at a time should not spend every
  run on tens of thousands of no-ops. A changed file is covered by forced
  re-processing.
- Note on the issue's premise: it says there is no persisted audio-stream
  information at query time, so every bulk run re-probes every silent
  video. That is no longer accurate. Upstream has since added an
  `asset_audio` table and `getForTranscription` reads it, so a silent
  video costs a queue round trip and one indexed read, not an ffprobe.
  The conclusion survives the correction — mark-complete is still right,
  and it is what the acceptance criteria ask for — but the cost being
  avoided is queue churn rather than repeated probing.
- An absent audio row has two readings, and only one of them is
  permanent. Either the file was probed and has no audio track, or it has
  never been probed by a version that records one: migration
  1777654048096 created the stream tables empty, nothing backfills them,
  and no later migration nulls `metadataExtractedAt` to force
  re-extraction, so a library that upgraded past that point has videos
  with audio and no row saying so.
- A video stream row separates the two, because any video the current
  extractor has seen has one. `getForTranscription` now selects
  `asset_video.assetId` as `videoStreamId`; with it, "no audio" is a
  permanent fact and is recorded, and without it the asset is left alone
  to be picked up once its metadata has been extracted. Writing it off on
  the absent audio row alone would silently exclude videos with perfectly
  good audio until someone ran a forced re-transcription of the library.
- Gating on `metadataExtractedAt` instead does not work: an asset
  extracted before that migration has the timestamp set and no stream
  row, so the two cases stay indistinguishable. Falling back to running
  the extraction does not work either — `extractAudio` rejects on ffmpeg
  error, so a genuinely silent video would fail its job rather than
  report "no audio".
- A hidden asset is still skipped without being marked, so unhiding it
  later puts it back in the queue. That case is not permanent the way an
  absent audio track is.

Single-asset re-run:
- `AssetJobName.REFRESH_TRANSCRIPT` on `POST /assets/jobs`, mapping to
  `AssetTranscribe` with `force: true`.
- Forced, because a finished asset's recorded offset sits at the end of
  the file: unforced, the re-run would resume, find nothing to do, and
  succeed having done nothing. `handleTranscribe` reads the offset only
  when not forced, which routes a forced run through `reset` and clears
  the earlier rows.
- Web: "Refresh transcript" in the asset viewer menu and "Refresh
  transcripts" in the five bulk-selection menus, both gated on the asset
  being a video and on the new transcription feature flag.

Retries and timeout:
- `TRANSCRIPTION_JOB_ATTEMPTS = 2`, pinned in `getJobOptions` rather than
  inherited from the global default. One retry catches the transient
  failures — the machine-learning service restarting, a worker killed
  mid-file — and costs little, because a retry resumes from the last
  committed chunk. The rest are deterministic (corrupt stream,
  undecodable codec, model out of memory) and re-hit the same wall at
  whole-video cost on a queue that runs one job at a time.
- `getJobTimeout(duration, multiplier)`: a whole-asset budget, checked
  between chunks. The per-chunk inference timeout bounds one model call
  and says nothing about the job; a long video is hundreds of calls, and
  a pathological file whose every chunk returns just under its ceiling
  would otherwise hold the queue for a day. Exceeding it returns Failed
  with the offset intact, so a later run resumes rather than restarting.
  The floor is the inference floor, and the check is only between chunks,
  so the first chunk of a run always goes ahead: no job is killed having
  transcribed nothing.

Job panel:
- `QueueName.Transcription` added to `asQueueItem` (icon, title,
  description) and to `QueuePanel`'s `queueDetails` with "all" and
  "missing" buttons, disabled when the feature is off.
- "All" now asks for confirmation, as face detection does: it truncates
  every transcript in the library and takes hours. The confirmation
  switch was rewritten as a lookup, because the old one relied on a
  fallthrough that a second case would have silently changed.
- New `transcription` server feature flag (`isTranscriptionEnabled`),
  which is what gates both the panel entry and the per-asset actions.

Tests:
- 8 transcription-service tests: a probed no-audio video is marked
  transcribed, an unextracted one is neither marked nor transcribed and
  is picked up once its stream rows exist, hidden stays unmarked, forced
  re-run ignores a completed offset and re-transcribes, the budget stops
  a run mid-file without marking it done, the first chunk always runs
  however short the budget, and a forced bulk run both truncates and
  enqueues.
- 2 asset-service tests: the refresh job is forced, and it touches only
  the asset it names.
- 5 medium tests on `streamForTranscriptionJob`: unprocessed queued,
  transcribed skipped, transcribed queued when forced, hidden excluded in
  both modes, non-video excluded in both modes.
- 3 medium tests on `getForTranscription`: an extracted video with no
  audio reads as probed and silent, one that was never extracted reads as
  unprobed, and an extracted video with audio reports its stream.
- Server unit suite green (2328 passed, 2 skipped). Web unit suite green
  (518 passed, 2 skipped). Server lint/format/typecheck, web
  lint/format/svelte-check/tsc all green.
- Medium suite: 406 passed, 24 failed in four files — ffprobe/exiftool
  and the workflow plugin binaries are missing from this environment. All
  four fail the same way on a clean checkout; none touch transcription.
- SQL query snapshots regenerated; the only diff is the video stream join
  and its selected column on `getForTranscription`.

Also fixed: `MediumTestContext.newJobStatus` built its insert from
`{ assetId }` alone and dropped every other field it was given, so
callers that passed a timestamp silently got the factory default. It now
forwards the whole dto. Existing callers were relying on the default
anyway, so nothing changed for them.

Not done / caveats:
- The Dart SDK was not regenerated, consistent with the rest of this
  branch: `mobile/openapi` already lacks the transcription models from
  issues #3–#7, so regenerating here would land five issues' worth of
  unrelated diff on this one. `mobile/lib/utils/openapi_patching.dart`
  was left alone for the same reason — patching in a default for a field
  the generated model does not have would be meaningless.
- The bulk "all" mode truncates every transcript before enqueueing, which
  is the reset semantic face detection uses. There is no "re-transcribe
  only these albums" or "only this date range"; the issue does not ask
  for one and the per-asset re-run covers the narrow case.
- The job budget is enforced between chunks, so a single chunk that hangs
  is bounded only by the inference timeout, not by the budget. That is
  deliberate — killing a model call mid-flight loses the chunk — but it
  means the effective ceiling is the budget plus one chunk timeout.
- The medium-test harness still cannot start its own database here:
  testcontainers fails against this host's Docker with "Log stream
  ended", as on the previous three issues. The medium tests were run
  against a manually started `ghcr.io/immich-app/postgres` with a
  throwaway global setup pointed at it. The setup and its config were
  deleted and are not part of the commit.
